# Retro

Run `retro.py` (beside this file) with Bash. The user never runs subcommands.

1. Run `retro.py prepare` (or `retro.py prepare --redo` if the user typed `/retro redo`).
2. Repeat its user-facing lines (the Opus refusal, the days-left refusal, or the plan-usage and format-drift lines) in your first message. If it printed the Opus refusal, stop there. If it printed days left, stop there, except for step 6.
3. Otherwise it printed a temp folder holding `metrics.json`, `digest.json`, `agent_a.json`, `agent_b.json` (each replaced by numbered pieces when split: see Splitting), `agent_c.json`, a brief per agent input (`brief_a.md`, `brief_b.md`, `brief_c.md`, or `brief_a_1.md`, … per piece) and `brief_web.md`, `previous.json`, `upstream.json`, `news_raw.json` and `draft.md`, and `/insights` is already running in the background. Start Agents A, B and C in parallel, in one message (below), then read `metrics.json` and this skill's `briefs/fixes.md` (where each fix goes), and write Findings for context (2), cost (5) and permissions (7), using this layout. Merge A's, B's and C's Findings with yours under `## Findings` in `draft.md`: drop duplicates (same problem and fix; keep the better one), then number everything by weight. The script flags candidates and writes no Finding; you judge each one. Skip a category with nothing worth saying.

   ```
   ### <n>. <category> · <project or "all"> · via Retro
   **Problem**: <one or two lines, with the numbers>
   **Solutions**:
   - **a.** <the exact change: file and edit, or command>. Fit: <…>. Adoption: <…>.
   ```

   Up to three self-contained solutions each. Order Findings by weight across categories, then number them from 1. No evidence lines, no status. For context, read each `instruction_files` entry with `over_limit` or growth, and propose moving the lines `fixes.md` places elsewhere and cutting its no-ops. Such a Finding may suggest `/doctor prompt-audit` (suggest it; don't run it). A permissions solution may point to the built-in `fewer-permission-prompts` skill. Deliberate denials (for example `railway`) stay denied.
   **Agents A, B and C**: spawn three subagents with `subagent_type: retro-worker` and `model: opus` in one message: Agent A (prompting quality (1) and rework (6)), Agent B (repeats (4) and workflows (8)) and Agent C (unused skills (3) and Overlap (9)). Each one's whole prompt is `Read <temp folder>/brief_<x>.md and follow it.` The brief holds its instructions, its rubric items, the Follow-through rules and the Finding layout; don't add to it. Each returns verdict rows, then Findings with no numbers and origin `via Retro`, in categories `prompting`/`rework`, `repeats`/`workflows` and `skills`/`overlap`. C's input is never split.
   **Splitting**: if `prepare` printed "input split into N pieces", `splits.json` maps `a` and/or `b` to piece files (`agent_a_1.json`, …) that replace `agent_a.json` / `agent_b.json`; C is never split. Spawn one `retro-worker` agent per piece, in the same message as the others, each told to read its piece's brief (`brief_a_1.md`, …). The piece brief already asks it for problems seen in only 2 of its Sessions (one line each, with the Session ids), so the reconcile agent can add them up across pieces, and for verdict rows that cover only its own Sessions. Then, per split group, spawn one `retro-worker` reconcile agent with `model: opus`: give it the pieces' returned drafts (verdict rows and Findings); it merges duplicates, combines their evidence before any frequency threshold (3 Sessions in one piece plus 3 in another counts as 6, so a problem below the bar in each piece can clear it), re-letters solutions (at most 3 per Finding) and returns one set of verdict rows and Findings for the main merge. Every piece carries `previous_findings`. The reconcile agent gives one verdict per previous Finding across all pieces (the problem came back in any piece: didn't work, or not adopted). A failed piece or reconcile agent is handled under Failures.
   **Follow-through**: `prepare` puts last Retro's Findings into the inputs (`previous_findings` in `agent_a/b/c.json` for each agent's own categories; `previous.json` holds the rest under `main`, plus `toolkit_updates` and `meta` text). `previous.json` is `null` when there was no previous Retro: write "No previous Retro." under `## Follow-through` and skip this. The briefs tell A, B and C to judge the `previous_findings` in their input and return the verdict rows first, then their Findings. Do the same yourself for `main`, `toolkit_updates` and `meta`. Each gets a verdict: worked, didn't work, not adopted, or no longer relevant. Judge from what changed (settings, installs, usage in the Window, whether the problem came back), and mark nothing in the old file. A not-adopted Finding comes back as a new Finding only if the problem got worse. An Overlap that still exists comes back every Retro, labelled "raised before". After a merge or removal that was applied, check the replacement got used. Agents return their verdicts as table rows `| <short summary of the fix> | <verdict> | <origin: Retro, /insights or web> |`, ahead of their Findings. Put all rows under `## Follow-through` in `draft.md` with the header `| Last month's fix | Verdict | Origin |`.
   **Toolkit updates**: read `upstream.json` yourself and write `## Toolkit updates` in `draft.md`, one item per entry in `skills`, `synced`, `plugins` and `claude_code`, in the Finding layout with **What changed** in place of **Problem** and no category, project or origin in the heading (`### <n>. <item>`, numbered after the Findings). Each item says what changed since `since` (a skill's repo commits from `commits[<repo>]`, repo-wide headlines since `since`, a plugin's releases, Claude Code's versions; one line each for skills from the same repo, with the commits that touch it if the headlines show it), its `uses` in the Window, and the exact `update` command as the solution. A `removed upstream` skill says upstream deleted it, so no update comes, and the user is its only maintainer now. Claude Code's releases are also the upstream of built-in commands, bundled skills and agents; say which new releases matter to items the user used. Skip entries with nothing behind. `clis` lists installed CLIs: each `outdated_used` entry is a Toolkit update like the others (its `update` command; its changelog is read later). Each `unused_outdated` line goes verbatim under `## Toolkit updates` as a plain bullet after the numbered items, with no analysis and no uninstall advice. `owned` covers Owned Skills (a `metadata.upstream` list of `{repo, path, base}`), as ordinary Findings under `## Findings` (category `skills`, origin `via Retro`), weighed with the rest. Never merge, edit or run git:
   - `tracked` with state `changed`: a "port this?" Finding naming the skill, the tracked source (`repo` `path`) and the `base`..HEAD range. Read the skill's own `SKILL.md`, then judge each changed file's `patch` (`commits` are repo-wide headlines, context only): raise only changes to content the skill kept, and skip dropped parts silently. State `removed upstream`: a Finding that upstream deleted the source, so the user is its only maintainer now.
   - `edited_installs`: the install's files differ from its locked version, so a later `npx skills update` would overwrite the edit. A Finding to own it: a folder `~/.claude/skills/<skill>/` (a real copy of the edited files) with `metadata: {upstream: [{repo: <repo>, path: <path>, base: <base>}]}` and a row in the skills README, removing the symlink and the lock entry through `npx skills remove <lock_key>` only after the copy exists.
   An install in `edited_installs` also listed under `skills` as behind gets no update command: `npx skills update` would overwrite the edit.
   - `no_provenance`: real folders with no `metadata.upstream`; only the first Retro fills it, so later Retros never raise it again. Check `~/.claude/skills/README.md` for each; one Finding for those it records as copied from a repo (name each, with the source from the README), to add `metadata: {upstream: [{repo, path, base}]}` using the commit it names. Skills the README shows as written by the user need nothing.
   A non-empty `errors` list goes under Failed parts. Changelog judgment beyond this comes later.
   Wait for all three results before step 4.
   **Failures**: `## Failed parts` lists every failed agent, `/insights` run and feed (from `errors` in `upstream.json` and `news_raw.json`), one line each, saying whether it was re-run ("re-run, succeeded", "re-run, failed", "re-run declined" or "not re-run" (feeds, `/insights`, `news`)). Never add a spending cap or a cost report.
   - Usage limit (an agent's result says so): that isn't a failure. Tell the user which agents paused, and to type "continue" after the reset. On "continue", re-run only those agents, with the same prompts and the same input files in the temp folder; list nothing for them. Don't run `commit` while an agent is paused; if the re-run hits the limit again, pause again.
   - Any other agent failure (crash, garbled output, timeout): offer one re-run of that agent and wait for approval. If the user declines, or the re-run fails, list it under Failed parts and go on. This covers the phase-2 web agent too. An `/insights` failure or a down feed isn't offered a re-run. Write `## Failed parts` last, just before `commit`, so it holds everything from steps 3 to the end.
   - A failure never stops the Retro or holds back the timestamp: still run step 4. The one exception is when A, B and C all failed (after any re-run): don't run `commit`, `rm -rf` the temp folder `prepare` printed, say so, and leave the state as it was.
   **`/insights` review**: after the merge above, run `retro.py insights <temp folder>` (it waits up to 5 minutes, so give the Bash call `timeout: 330000`) and read the `insights.json` it prints. If it holds `error`, list `/insights` under `## Failed parts` with the error and say it wasn't re-run; leave the review section with "`/insights` failed." and go on. Otherwise `sections` holds the text of `section-friction`, `section-features`, `section-patterns` and `section-horizon`; ignore everything else in the report. Give each item (a friction category, a suggested CLAUDE.md line, feature or pattern, horizon idea) exactly one verdict against your merged Findings and the Window: **confirm** or **amend** (it holds, or holds with a changed fix) becomes a Finding in the usual layout, tagged `via /insights`, numbered with the rest; **merge** joins it to an existing Finding (add its fix as a solution, or note it agrees; no new Finding); **drop** (already handled, stale, contradicted by the transcripts, or not worth it) is listed once with its reason. A stale item is dropped. A suggested CLAUDE.md line that `fixes.md` places elsewhere is amended to go there. Under ``## `/insights` review`` write the date range from `date_range`, the counts as `Confirmed: n · Merged: n · Amended: n · Dropped: n`, then each dropped item as a bullet with its reason.
   **Web solutions (phase 2)**: after the `/insights` review, build the problem list: the roughly five most frequent problems among the numbered Findings (by the counts in their Problem lines), each searched even when the Toolkit already has a fix. Run `retro.py news <temp folder> <category>...` first, naming the categories of those problems (prompting, context, skills, repeats, cost, rework, permissions, workflows, overlap); (if it fails, list it under `## Failed parts` and go on without news) it scores `news_raw.json` and writes `news.json`: `items` (official ones plus the best 40 others, each with source, title, url, date, body), `html_sources` and `errors`. List each of `news_raw.json`'s `errors` (a feed that was down) under `## Failed parts`, not re-run. Spawn one subagent with `subagent_type: retro-worker` and `model: sonnet` whose prompt is `Read <temp folder>/brief_web.md and follow it.`, then the list, one line per problem (the Finding's number, its category and its Problem text), then one line naming the tools the user works with in the Window. The brief covers `news.json`, the outdated items in `upstream.json`, the search rules and the return format. It returns per-problem solutions, Meta items (`### <n>. <title>`, **What changed**, **Solutions**, source URL last) and **What changed** items for used outdated Toolkit items. Write the Meta items and changelog items under `## Meta` and `## Toolkit updates` (numbered after the rest), kept short. Then add its per-problem solutions yourself as further lettered solutions under the matching Finding, with fit and adoption notes, at most 3 solutions in all per Finding: when over, drop the weakest web solution first, never one that uses something already installed, then re-letter a, b, c. Put the source URL at the end of the solution's Adoption note. Do this before numbering the Findings by weight. If the agent fails, handle it under Failures above.
4. Run `retro.py commit <temp folder>/draft.md`. Do not write frontmatter yourself; `commit` sets the Findings count.
5. Tell the user the findings file path it printed.
6. If `prepare` printed a statusline hint (on a refusal too), last of all offer the edit, and make it only after a yes (a decline isn't stored):
   - statusLine names a script: append `~/.claude/skills/retro/retro.py status`, joined to the existing output with ` · `;
   - statusLine is an inline command: append `; ~/.claude/skills/retro/retro.py status`;
   - no statusLine: set it to `~/.claude/skills/retro/retro.py status`.
