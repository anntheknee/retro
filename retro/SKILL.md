# Retro

Run `retro.py` (beside this file) with Bash. The user never runs subcommands.

1. Run `retro.py prepare` (or `retro.py prepare --redo` if the user typed `/retro redo`).
2. Repeat its user-facing lines (the days-left refusal, or the plan-usage and format-drift lines) in your first message. If it printed days left, stop there, except for step 6.
3. Otherwise it printed a temp folder holding `metrics.json`, `digest.json`, `agent_a.json`, `agent_b.json` (each replaced by numbered pieces when split: see Splitting), `agent_c.json`, `previous.json`, `upstream.json`, `news_raw.json` and `draft.md`, and `/insights` is already running in the background. Start Agents A, B and C in parallel, in one message (below), then read `metrics.json` and write Findings for context (2), cost (5) and permissions (7), using this layout. Merge A's, B's and C's Findings with yours under `## Findings` in `draft.md`: drop duplicates (same problem and fix; keep the better one), then number everything by weight. The script flags candidates and writes no Finding; you judge each one. Skip a category with nothing worth saying.

   ```
   ### <n>. <category> · <project or "all"> · via Retro
   **Problem**: <one or two lines, with the numbers>
   **Solutions**:
   - **a.** <the exact change: file and edit, or command>. Fit: <…>. Adoption: <…>.
   ```

   Up to three self-contained solutions each. Order Findings by weight across categories, then number them from 1. No evidence lines, no status. For context, `instruction_files` entries with `over_limit` or growth may suggest `/doctor prompt-audit` (suggest it; don't run it). A permissions solution may point to the built-in `fewer-permission-prompts` skill. Deliberate denials (for example `railway`) stay denied.
   **Agent A** (prompting quality (1) and rework (6)): spawn one subagent with `model: opus`. Tell it to read `<temp folder>/agent_a.json` (or its piece), `~/.claude/skills/retro/rubric.md` (items P1-P12, plus C2, C3, C6 and C8 for rework) and nothing else, and to return only Findings in the layout above, with categories `prompting` and `rework`, no numbers, origin `via Retro`. `agent_a.json` holds each Session's typed prompts; turns with `flags` (interrupted, steered, edit_churn, error_loop) carry `prev_tail`, the end of Claude's previous reply. When the digest isn't enough it runs `~/.claude/skills/retro/retro.py context <session> <i> <temp folder>` for one turn. It never reads raw transcripts. Vague prompts count only when they led to rework or wasted reads. Fixes are exact: a CLAUDE.md line, a hook, a habit with the keystroke. 
   **Agent B** (repeats (4) and workflows (8)): spawn one subagent with `model: opus`, in the same message as A and C. Tell it to read `<temp folder>/agent_b.json` (or its piece), `~/.claude/skills/retro/rubric.md` (items W1-W8, plus C5 and C6) and nothing else, and to return only Findings in the layout above, with categories `repeats` and `workflows`, no numbers, origin `via Retro`. `agent_b.json` holds every typed prompt per Session plus the script's repeat candidates: `repeated_prompts`, `long_prompt_duplicates`, `similar_openings`, `similar_agent_prompts`, and Bash heads and tool sequences seen in 3+ Sessions. Candidates are leads, not proof: it confirms each against the prompts. A repeated question or correction is a `repeats` Finding whose fix is a CLAUDE.md line or a habit. A `workflows` Finding names the trigger and proposes the matching form: a skill (a procedure Claude follows when asked), a hook (must happen every time, no asking) or a subagent (the same worker spawned with the same instructions). A proposed skill meets the W8 bar: its name, its one-line description, the steps in outline, which steps are a script, and `disable-model-invocation: true` if it has side effects. It never reads raw transcripts.
   **Agent C** (unused skills (3) and Overlap (9)): spawn one subagent with `model: opus`, in the same message as A and B. Tell it to read `<temp folder>/agent_c.json`, `~/.claude/skills/retro/rubric.md` (items S1-S7) and nothing else (bar the candidate `SKILL.md` files below), and to return only Findings in the layout above, with categories `skills` and `overlap`, no numbers, origin `via Retro`. `agent_c.json` holds the Toolkit table (`items`: name, origin, auto, description, `uses` in the Window, `lifetime` count; `plugins`: used, unused or "hooks only, can't tell"; `dead_slash`: slash name → times typed, for names typed in the Window that match no Toolkit item) and every typed prompt per Session. It never splits its input. It finds tasks the user did by hand or Claude improvised that an installed item's description clearly covers (S1), confirming each against the prompt. Zero uses alone is not a Finding. A fix names the skill and the exact habit: the slash name to type, or a description edit when auto-triggering missed. For a plugin with status `unused`, offer `claude plugin uninstall <id>`; for "hooks only, can't tell" or "unused, but ships hooks", say so and don't advise removal.
   C also finds Overlap (category `overlap`): Toolkit items whose descriptions cover the same job. It judges from descriptions and reads a full `SKILL.md` (under `~/.claude/skills/` or the plugin's install path) only for a candidate set; `uses` is evidence, not the detector. Verdict per Overlap: a member with 0 `uses` gets pick-one (uninstall it); if no member was used, C picks the better fit; if a built-in wins, the verdict is to stop using your own copy. The alternative is merge-and-own, whose solution gives the new name, what each original contributes, what's dropped, and the sources to track. It says the Owned Skill goes in `~/.claude/skills/<name>/` with `metadata: {upstream: [{repo, path, base}]}` and a row in the skills README, and that the originals are removed through their own installers (`npx skills remove`, `claude plugin uninstall`, `rm` for hand copies). A plugin can only be removed whole and a built-in can't be removed; the Finding says so. If the 0-use member is a plugin, follow the plugin rule above instead (no removal advice for a plugin that ships hooks or used items); don't raise a second Finding for the same plugin. Each verdict carries its reasoning. Tell C to also sort `dead_slash` names into removed-skill habits (a skill you used to have), typos and noise, and report only the habits in one informational Finding (no forwarding stubs, no fix to apply). The Retro never merges, uninstalls or runs git; the user asks for that later.
   **Splitting**: if `prepare` printed "input split into N pieces", `splits.json` maps `a` and/or `b` to piece files (`agent_a_1.json`, …) that replace `agent_a.json` / `agent_b.json`; C is never split. Spawn one agent per piece, telling each piece agent to also return, after its Findings, problems seen in only 2 of its Sessions (one line each, with the Session ids), so the reconcile agent can add them up across pieces, in the same message as the others, each with that agent's usual instructions and its piece as the input file (every B piece also holds the whole-Window repeat lists). Then, per split group, spawn one `model: opus` reconcile agent: give it the pieces' returned drafts (verdict rows and Findings); it merges duplicates, combines their evidence before any frequency threshold (3 Sessions in one piece plus 3 in another counts as 6, so a problem below the bar in each piece can clear it), re-letters solutions (at most 3 per Finding) and returns one set of verdict rows and Findings for the main merge. Every piece carries `previous_findings`, and each piece agent's verdict rows cover only its own Sessions: tell it to say, for each previous Finding, whether the problem came back in them. The reconcile agent gives one verdict per previous Finding across all pieces (the problem came back in any piece: didn't work, or not adopted). A failed piece or reconcile agent is handled under Failures.
   **Follow-through**: `prepare` puts last Retro's Findings into the inputs (`previous_findings` in `agent_a/b/c.json` for each agent's own categories; `previous.json` holds the rest under `main`, plus `toolkit_updates` and `meta` text). `previous.json` is `null` when there was no previous Retro: write "No previous Retro." under `## Follow-through` and skip this. Include this in each of A's, B's and C's prompts (the bullets above don't repeat it): judge the `previous_findings` in your input, and return the verdict rows first, then your Findings. Do the same yourself for `main`, `toolkit_updates` and `meta`. Each gets a verdict: worked, didn't work, not adopted, or no longer relevant. Judge from what changed (settings, installs, usage in the Window, whether the problem came back), and mark nothing in the old file. A not-adopted Finding comes back as a new Finding only if the problem got worse. An Overlap that still exists comes back every Retro, labelled "raised before". After a merge or removal that was applied, check the replacement got used. Agents return their verdicts as table rows `| <short summary of the fix> | <verdict> | <origin: Retro, /insights or web> |`, ahead of their Findings. Put all rows under `## Follow-through` in `draft.md` with the header `| Last month's fix | Verdict | Origin |`.
   **Toolkit updates**: read `upstream.json` yourself and write `## Toolkit updates` in `draft.md`, one item per entry in `skills`, `synced`, `plugins` and `claude_code`, in the Finding layout with **What changed** in place of **Problem** and no category, project or origin in the heading (`### <n>. <item>`, numbered after the Findings). Each item says what changed since `since` (a skill's repo commits from `commits[<repo>]`, repo-wide headlines since `since`, a plugin's releases, Claude Code's versions; one line each for skills from the same repo, with the commits that touch it if the headlines show it), its `uses` in the Window, and the exact `update` command as the solution. A `removed upstream` skill says upstream deleted it, so no update comes, and the user is its only maintainer now. Claude Code's releases are also the upstream of built-in commands, bundled skills and agents; say which new releases matter to items the user used. Skip entries with nothing behind. `clis` lists installed CLIs: each `outdated_used` entry is a Toolkit update like the others (its `update` command; its changelog is read later). Each `unused_outdated` line goes verbatim under `## Toolkit updates` as a plain bullet after the numbered items, with no analysis and no uninstall advice. `owned` covers Owned Skills (a `metadata.upstream` list of `{repo, path, base}`), as ordinary Findings under `## Findings` (category `skills`, origin `via Retro`), weighed with the rest. Never merge, edit or run git:
   - `tracked` with state `changed`: a "port this?" Finding naming the skill, the tracked source (`repo` `path`) and the `base`..HEAD range. Read the skill's own `SKILL.md`, then judge each changed file's `patch` (`commits` are repo-wide headlines, context only): raise only changes to content the skill kept, and skip dropped parts silently. State `removed upstream`: a Finding that upstream deleted the source, so the user is its only maintainer now.
   - `edited_installs`: the install's files differ from its locked version, so a later `npx skills update` would overwrite the edit. A Finding to own it: a folder `~/.claude/skills/<skill>/` (a real copy of the edited files) with `metadata: {upstream: [{repo: <repo>, path: <path>, base: <base>}]}` and a row in the skills README, removing the symlink and the lock entry through `npx skills remove <lock_key>` only after the copy exists.
   An install in `edited_installs` also listed under `skills` as behind gets no update command: `npx skills update` would overwrite the edit.
   - `no_provenance`: real folders with no `metadata.upstream`; only the first Retro fills it, so later Retros never raise it again. Check `~/.claude/skills/README.md` for each; one Finding for those it records as copied from a repo (name each, with the source from the README), to add `metadata: {upstream: [{repo, path, base}]}` using the commit it names. Skills the README shows as written by the user need nothing.
   A non-empty `errors` list goes under Failed parts. Changelog judgment beyond this comes later.
   Wait for all three results before step 4.
   **Failures**: `## Failed parts` lists every failed agent, `/insights` run and feed (from `errors` in `upstream.json` and `news_raw.json`), one line each, saying whether it was re-run ("re-run, succeeded", "re-run, failed", "re-run declined" or "not re-run" (feeds, `/insights`, `news`)). Never add a spending cap or a cost report.
   - Usage limit (an agent's result says so): that isn't a failure. Tell the user which agents paused, and to type "continue" after the reset. On "continue", re-run only those agents, with the same prompts and the same input files in the temp folder; list nothing for them. Don't run `commit` while an agent is paused; if the re-run hits the limit again, pause again.
   - Any other agent failure (crash, garbled output, timeout): offer one re-run of that agent and wait for approval. If the user declines, or the re-run fails, list it under Failed parts and go on. This covers the phase-2 web agent too. An `/insights` failure or a down feed isn't offered a re-run. Write `## Failed parts` last, just before `commit`, so it holds everything from steps 3 to the end.
   - A failure never stops the Retro or holds back the timestamp: still run step 4. The one exception is when A, B and C all failed (after any re-run): don't run `commit`, `rm -rf` the temp folder `prepare` printed, say so, and leave the state as it was.
   **`/insights` review**: after the merge above, run `retro.py insights <temp folder>` (it waits up to 5 minutes, so give the Bash call `timeout: 330000`) and read the `insights.json` it prints. If it holds `error`, list `/insights` under `## Failed parts` with the error and say it wasn't re-run; leave the review section with "`/insights` failed." and go on. Otherwise `sections` holds the text of `section-friction`, `section-features`, `section-patterns` and `section-horizon`; ignore everything else in the report. Give each item (a friction category, a suggested CLAUDE.md line, feature or pattern, horizon idea) exactly one verdict against your merged Findings and the Window: **confirm** or **amend** (it holds, or holds with a changed fix) becomes a Finding in the usual layout, tagged `via /insights`, numbered with the rest; **merge** joins it to an existing Finding (add its fix as a solution, or note it agrees; no new Finding); **drop** (already handled, stale, contradicted by the transcripts, or not worth it) is listed once with its reason. A stale item is dropped. Under ``## `/insights` review`` write the date range from `date_range`, the counts as `Confirmed: n · Merged: n · Amended: n · Dropped: n`, then each dropped item as a bullet with its reason.
   **Web solutions (phase 2)**: after the `/insights` review, build the problem list: the roughly five most frequent problems among the numbered Findings (by the counts in their Problem lines), each searched even when the Toolkit already has a fix. Run `retro.py news <temp folder> <category>...` first, naming the categories of those problems (prompting, context, skills, repeats, cost, rework, permissions, workflows, overlap); (if it fails, list it under `## Failed parts` and go on without news) it scores `news_raw.json` and writes `news.json`: `items` (official ones plus the best 40 others, each with source, title, url, date, body), `html_sources` and `errors`. List each of `news_raw.json`'s `errors` (a feed that was down) under `## Failed parts`, not re-run. Spawn one subagent with `model: sonnet` and give it the list, one line per problem (the Finding's number, its category and its Problem text), plus `<temp folder>/news.json`, `upstream.json`'s `plugins` and `claude_code` entries and the `clis.outdated_used` entries (Toolkit items used in the Window and behind upstream). For each `html_sources` entry it runs WebFetch with the given narrow prompt. For each used outdated item it reads the changelog since the cursor (a plugin's `releases_since_cursor`; for a CLI, its GitHub releases or changelog page found through WebFetch) and returns **What changed** against the problem list: only what matters to how the user uses it. For each news item it keeps one only if it changes how an installed Toolkit item should be used or addresses a detected problem, and returns it either as a solution for that problem's Finding or as a Meta item (`### <n>. <title>`, **What changed**, **Solutions** with the exact thing to install or change, source URL last); it drops the rest. Meta items and changelog items stay short, and you write them under `## Meta` and `## Toolkit updates` (numbered after the rest). Tell it: use WebSearch only for follow-ups ("fix for X", "Y vs Z"), never for discovery, since it has no date filter; use WebFetch for article bodies it decides to read; run no search without a problem behind it; and return, per problem, up to three solutions in the Finding layout (`- **a.** <the exact thing to install or change: command, repo or setting>. Fit: <…>. Adoption: <…>.`) each with its source URL, skipping any that name nothing concrete. Then add them yourself as further lettered solutions under the matching Finding, with fit and adoption notes, at most 3 solutions in all per Finding: when over, drop the weakest web solution first, never one that uses something already installed, then re-letter a, b, c. Put the source URL at the end of the solution's Adoption note. Do this before numbering the Findings by weight. If the agent fails, handle it under Failures above.
4. Run `retro.py commit <temp folder>/draft.md`. Do not write frontmatter yourself; `commit` sets the Findings count.
5. Tell the user the findings file path it printed.
6. If `prepare` printed a statusline hint (on a refusal too), last of all offer the edit, and make it only after a yes (a decline isn't stored):
   - statusLine names a script: append `~/.claude/skills/retro/retro.py status`, joined to the existing output with ` · `;
   - statusLine is an inline command: append `; ~/.claude/skills/retro/retro.py status`;
   - no statusLine: set it to `~/.claude/skills/retro/retro.py status`.
